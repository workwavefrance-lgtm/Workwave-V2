### L01 · 18/04/2026 — Bug espace dans BASE_URL

un espace invisible (notamment nbsp `\u00A0`) dans `NEXT_PUBLIC_BASE_URL` casse les liens emails (`https://workwave.fr /artisan/...`). Toujours nettoyer avec `.replace(/\s+/g, "")` côté serveur, pas juste `.trim()`. Ne jamais supposer qu'une variable d'env est propre.


### L02 · 18/04/2026 — Vérification TypeScript

`npx tsc --noEmit` peut remonter de fausses erreurs venant de `.next/types/` (cache Next 16). Réflexe : `rm -rf .next && npx tsc --noEmit` avant de conclure qu'il y a un problème de typage.


### L03 · 18/04/2026 — Audit sans données

ne jamais affirmer une tendance d'un concurrent SEO sur la base d'une seule page. Échantillonner au moins 3-5 pages OU être explicite sur la limite ("vu sur 1 page seulement, à reconfirmer").


### L04 · 18/04/2026 — Logs scraping trompeurs

le script `sirene_vienne.py` affiche "X pros insérés" mais ce X = nombre envoyés à upsert, PAS insertions nettes. Avec `ignore_duplicates=True`, beaucoup sont rejetés en silence. Toujours requêter Supabase APRÈS le scraping pour le vrai count net (`SELECT COUNT(*) FROM pros WHERE category_id = X`). Exemple réel : "1214 vitriers insérés" → 19 nets en base car NAF 4334Z déjà absorbé par peintres.


### L05 · 18/04/2026 — NAF Sirene trop génériques pour scraper précisément

un seul code NAF couvre souvent plusieurs métiers (4329B = pisciniste + ascensoriste + autres ; 4334Z = peintre + vitrier ; 4321A = électricien + vidéosurveillance ; 8121Z = ménage + nettoyage pro). Conséquence : faux positifs massifs ("REGIONAL ASCENSEURS" classé pisciniste). Pour un scraping précis, soit (a) filtrer en post-traitement par regex sur le nom (PISCIN, VITRER, RAMON…), soit (b) enrichir via Apify Google Maps (le métier réel sort des avis), soit (c) accepter pour le SEO mais marquer la donnée comme "à valider". JAMAIS supposer qu'un NAF correspond 1:1 à un métier.


### L06 · 18/04/2026 — dotenv + tsx → toujours `override: true`

`tsx` pré-injecte certaines variables `.env.local` en chaîne vide AU DÉMARRAGE du script (avant que `dotenv.config()` tourne). Sans `override: true`, dotenv refuse d'écraser ces vars vides (comportement par défaut). Symptôme : log "injected env (12) from .env.local" alors qu'il y en a 13 dans le fichier ; appel API qui échoue avec "Could not resolve authentication method" pour ANTHROPIC_API_KEY. Pattern obligatoire dans tous les scripts : `dotenv.config({ path: path.resolve(process.cwd(), ".env.local"), override: true })`. Le script `scripts/generate-seo-content.ts` utilise déjà ce pattern — l'utiliser comme référence quand on crée un nouveau script.


### L07 · 18/04/2026 — Next.js routes : un seul nom de param dynamique par position d'URL

Next.js refuse `app/[metier]/[location]/page.tsx` ET `app/[metier]/[specialite]/[ville]/page.tsx` côte à côte. Erreur fatale au boot du dev server : `You cannot use different slug names for the same dynamic path ('location' !== 'specialite')`. La règle : à chaque NIVEAU d'URL, le segment dynamique doit avoir EXACTEMENT le même nom dans toutes les routes. Solution : nommer pareil partout (ex. garder `[location]` au niveau 2) et aliaser à l'intérieur de la page (`const specialite = location;` avec un commentaire). Toujours vérifier l'arborescence existante AVANT de créer un nouveau dossier dynamique. Le `npm run build` ne détecte PAS cette erreur — seul le dev server crash. Réflexe : démarrer le dev server après création d'une route dynamique.


### L08 · 18/04/2026 — FK Postgres oubliées dans cleanup hard-delete

avant tout DELETE en cascade manuel d'une table parent (ex. `categories`), lister TOUTES les tables enfant via `information_schema` ou `\d categories` dans psql. Le script `cleanup-drop-categories.ts` v1 a oublié `seo_guides.category_id` : pros + seo_pages déjà supprimés, puis l'étape DELETE categories a planté avec `violates foreign key constraint "seo_guides_category_id_fkey"`. Heureusement c'était récupérable (juste refaire l'étape manquante), mais on aurait pu se retrouver dans un état moitié-moitié. Réflexe avant chaque cleanup : `SELECT conrelid::regclass FROM pg_constraint WHERE confrelid='categories'::regclass AND contype='f';` pour lister toutes les tables qui pointent vers la table à drop. Le script est désormais corrigé (5 étapes au lieu de 4) et accepte `--slugs` pour être réutilisable.


### L09 · 18/04/2026 — Reclassement par regex >> re-scraping pour catégories absorbées par NAF ambigu

quand une catégorie cible (serrurier, vitrier, climaticien) est vide à cause d'un NAF partagé avec une catégorie absorbante (menuisier, peintre, chauffagiste), un UPDATE `category_id` par regex sur `pros.name` (`SERRUR`, `VITR|MIROIT`, `CLIM|FROID`) est BEAUCOUP plus rapide et précis qu'un re-scraping Sirene + filtre. Bonus : les fiches sont déjà nettoyées et potentiellement enrichies par Apify, et 0 API call. Précondition obligatoire : aucun pro `claimed_by_user_id != null` dans le lot (le script `reclass-pros-by-regex.ts` refuse de tourner sinon, parce que reclasser la fiche d'un pro abonné peut casser sa visibilité). Mini-sprint 18/04 : 33 reclassements (10+5+18) en 1 minute, vs ~1h de re-scraping + dedup côté Python pour le même résultat.


### L10 · 18/04/2026 — Slug département trop laxiste : `xxx-NN` matchait n'importe quel département

`parseDepartmentSlug()` utilise la regex `^(.+)-(\d{2,3})$` puis `getDepartmentBySlug()` ne filtrait que sur le `code` Postgres. Conséquence : `/macon/saint-savin-86`, `/plombier/n-importe-quoi-86`, etc. étaient résolus comme département Vienne (code 86) et servaient la page liste complète du département (200 OK avec 997 pros) au lieu d'un 404. Duplicate content latent massif (N URLs invalides servent toutes le même contenu) et le redirect 308 Phase D ne se déclenchait JAMAIS sur ces URLs (parce que résolues comme `type === "department"`, pas `"city"`). **Fix** : après lookup par code, regénérer le slug canonique via `generateDepartmentSlug(dept)` et le comparer **strictement** avec le slug entrant ; si différent, retourner `null` (la page tombe en `notFound()` → 404 propre). Réflexe à appliquer pour toute fonction `getXBySlug` qui parse le slug en plusieurs morceaux : ne PAS se contenter d'un lookup partiel sur un seul morceau ; toujours revérifier que le slug entier correspond à ce qu'on aurait régénéré pour l'objet trouvé. Tests pré-déploy obligatoires : (a) slug canonique → 200, (b) slug invalide qui matche le pattern → 404, (c) slug ville réel sans suffixe → 308 inchangé.


### L11 · 18/04/2026 — `loading.tsx` casse `notFound()` et `permanentRedirect()` en streaming Suspense

si une route a un `loading.tsx` (Suspense fallback), Next.js 16 stream le HTML du fallback avec status 200 AVANT que la `Page()` async puisse throw. Conséquence : `notFound()` et `permanentRedirect()` appelés dans la `Page()` ne fonctionnent PLUS — le client reçoit du HTML avec code 200 au lieu de 404/308, et le contenu rendu est le skeleton du loading. Symptôme typique : `console.log` montre l'appel à `notFound()` (et le code après ne s'exécute pas), mais HTTP code = 200. Bug confirmé en `next dev` ET en `next start` (pas un bug spécifique au dev mode). Solutions : (1) supprimer le `loading.tsx` de la route concernée — perd le skeleton mais le redirect/notFound fonctionne, (2) déplacer le check vers `generateMetadata()` qui s'exécute AVANT le streaming, (3) middleware avec redirect HTTP. Cas réel résolu 18/04 : `app/(public)/[metier]/[location]/loading.tsx` empêchait le redirect 308 vers la page département pour villes sans pros — supprimé pour faire fonctionner le noindex fix. Toujours tester avec `curl -o /dev/null -w "%{http_code} %{redirect_url}\\n"` pour vérifier le STATUS CODE, pas juste le contenu rendu. Pour debug rapide : créer une route minimale `/test-notfound/page.tsx` qui appelle juste `notFound()` — si elle renvoie 404, le bug vient de la route originale (loading.tsx, parent component, etc.).


### L12 · 27/04/2026 — RÈGLE STRICTE noindex et robots.txt (à vie)

le site grossit (226k+ pros, 4293 communes, 240k+ URLs sitemap, 3140 indexées et croissant). Toute erreur de noindex ou de Disallow se paie en milliers d'URLs perdues pour le SEO. Historique des dégâts : (1) `/artisan/[slug]` avec condition `hasContent` trop stricte → 9810 fiches noindexées en GSC pendant des semaines ; (2) `/[metier]/[ville]` sans pros noindex → 6000 URLs pollutives, fix tardif via redirect 308 Phase D. **À PARTIR DE MAINTENANT** :
  - **JAMAIS d'ajout de `robots: { index: false }` sur une page publique sans : (a) compter les URLs impactées via un script SQL, (b) écrire le count dans le commit message, (c) validation explicite de Willy dans le chat.** Pas de "ça me semble logique de noindex ces pages thin" en autonomie.
  - **JAMAIS d'ajout dans `app/robots.ts` Disallow sans la même procédure** (count + commit + validation).
  - **Pages où le noindex EST AUTORISÉ sans demander** (pas de valeur SEO + sécurité/RGPD) : `/admin/*`, `/pro/dashboard/*`, `/pro/reclamer/*`, `/pro/connexion`, `/pro/mot-de-passe-oublie`, `/pro/reinitialiser-mot-de-passe`, `/auth/*`, `/test*`, `/artisan/*/supprimer`, `/deposer-projet/supprimer`, `/unsubscribe*`, `/unsubscribe-all*`. Toutes ces pages SONT déjà noindex dans le code, ne PAS y toucher sauf demande explicite.
  - **Pages où le noindex EST INTERDIT (mort SEO immédiate)** : `/` (home), `/a-propos`, `/cgu`, `/cgv`, `/mentions-legales`, `/recherche`, `/deposer-projet`, `/pro` (landing), `/blog` et `/blog/[slug]`, `/[metier]` (page racine métier proximity), `/[metier]/[location]` (cat × dept ou cat × ville), `/[metier]/[specialite]/[ville]`, `/[metier]/guide`, `/artisan/[slug]` (TOUTES les fiches pros, même squelettes — Sirene + nom + ville + SIRET = assez pour Google).
  - **Pour les pages "thin content" perçues** : NE JAMAIS noindex. Solutions autorisées dans cet ordre :
    1. Redirect 308 vers une page parente plus riche (ex. `/[metier]/[ville]` vide → `/[metier]/dept`)
    2. Enrichir le contenu (description IA, schema enrichi, FAQ, maillage interne)
    3. Réduire la priority dans le sitemap (passer de 0.5 à 0.3)
    4. Laisser Google décider (il sait classer les pages faibles, c'est son métier)
  - **Vérification automatique** : un script `scripts/audit-noindex-robots.ts` scan le code et alerte si une page publique stratégique a un noindex. À lancer avant tout commit qui touche aux metadata. Idéalement en pre-commit hook.
  - **En cas de doute** : NE PAS noindex. Demander à Willy. Le coût d'un noindex en trop est beaucoup plus élevé que le coût d'une page squelette indexée (Google a son propre algo de classement).

### L15 · 28/04/2026 — `count: "exact"` Supabase timeout middleware sur grosses tables

`lib/queries/admin-pros.ts` faisait `.select(SELECT, { count: "exact" })` sur la table `pros` qui contient 226 478 rows. Conséquence : `SELECT COUNT(*)` prenait plusieurs secondes → timeout du `fetch` interne du middleware vers `/api/admin/auth/check` → redirect `/admin/login?error=unauthorized` avec message "Vous n'avez pas les droits administrateur". Symptôme utilisateur : "je clique sur Professionnels et ça me déconnecte" alors que tout le reste de l'admin fonctionnait. Réserver `"exact"` pour les listings courts (<10 000 rows) ou les exports où la précision compte. Si le count exact est nécessaire pour de grosses tables, le faire dans une requête séparée non bloquante.


### L16 · 29/04/2026 — Sitemap doit toujours répondre < 5s par sub-sitemap (timeout Googlebot ~30s)

`/sitemap/2.xml` (cat × ville) prenait **26 secondes** en cold cache à cause de (a) `count: "exact"` sur table pros 226k rows, (b) pagination Supabase 1000 par 1000 = ~50 round-trips, (c) parcours de 500 villes. Conséquence : Googlebot timeout au fetch → GSC affiche "Impossible de récupérer le sitemap" → 0 page découverte via sitemap → indexation à plat. Fix : count estimated + PAGE_SIZE 5000 (max Supabase) + TOP_CITIES réduit à 300 + `revalidate = 86400` (cache 24h Vercel). Résultat : 26s → 0,4s. **Règle stricte pour l'avenir** : (1) toute requête de comptage sur `pros` ou autre table > 50k rows doit utiliser `count: "estimated"`, JAMAIS `count: "exact"` (déjà documenté le 28/04 mais à appliquer partout, notamment sitemap.ts et sitemap-index.xml). (2) Tout fetch Supabase paginé doit utiliser PAGE_SIZE = 5000 (max), pas 1000. (3) Toute route sitemap doit avoir `export const revalidate = 86400` pour cacher la réponse 24h côté Vercel Edge. (4) Avant tout déploiement sitemap, lancer `scripts/audit-sitemap-perf.ts` qui mesure le temps de chaque sub-sitemap. Si l'un dépasse 5s, NE PAS push. Le code est correct mais un sitemap lent est aussi pénalisant qu'un sitemap cassé.

### L18 · 29/04/2026 — ADC `gcloud auth application-default login` doit être lancé AVEC `--scopes` pour Indexing API

par défaut, `gcloud auth application-default login` ne demande que le scope `cloud-platform`, qui ne couvre PAS l'API Indexing. Symptôme : tous les pings remontent l'erreur `Request had insufficient authentication scopes`, peu importe ce qu'on met dans le code TS. Fix : relancer la commande avec `--scopes="https://www.googleapis.com/auth/indexing,https://www.googleapis.com/auth/cloud-platform"`. Au moment de l'écran de consentement OAuth, on voit alors apparaître "Voir et soumettre des URL pour indexation" dans la liste des permissions — confirmation que c'est bien chargé. **Règle pour l'avenir** : tout script qui appelle une API Google scope-spécifique (Indexing, Search Console API, YouTube, Drive, Gmail, etc.) doit documenter dans son header le scope nécessaire et le command line `gcloud auth application-default login --scopes=...` exact à utiliser. Le `scopes` qu'on passe à `new google.auth.GoogleAuth({ scopes })` ne sert QU'À LA SÉLECTION DU TOKEN — il ne provisionne pas le scope si l'ADC ne le contient pas. Pour les credentials de service account JSON (option qu'on n'a pas pu prendre vu org policy `iam.disableServiceAccountKeyCreation`), pas de problème de scope car ça utilise des JWT signés. Pour ADC user-credentials, scope = baked-in à l'auth.

### L21 · 30/04/2026 — Cold email mass : sender authentifié + tracking headers + footer GDPR token = trio non-négociable

avant ce sprint, les batches Brevo cold envoyaient depuis `workwave.france@gmail.com` (Gmail Freemail = ~80% spam depuis Feb 2024 : refus Google/Yahoo/Microsoft des Freemail en bulk B2B), sans header `X-Mailin-Track-Click`, et avec un footer "Se désinscrire" hardcodé sans token. Trois bugs en un. **Le trio à appliquer SYSTÉMATIQUEMENT pour tout cold email mass** :

### L23 · 30/04/2026 — Sitemap chargeait 97% MOINS d'URLs que prévu : pagination buguée à cause du PostgREST max-rows par défaut

`app/sitemap.ts` avait `SUPABASE_PAGE_SIZE = 5000` et faisait `.range(offset, offset + 4999)` pour charger 5000 rows par round-trip. ### L39 · 26/05/2026 — Race condition double-claim sur SELECT-then-INSERT idempotent = UNIQUE INDEX partiel obligatoire

un pattern courant en idempotence : "SELECT existing row WHERE user=X ; si pas trouvé alors INSERT".
